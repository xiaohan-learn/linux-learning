## 一、进程与信号（6 题）

**Q1. `fork` 的原理和坑？**
- 定位：创建子进程，**写时复制 COW**，不是立刻拷贝，缺页（写入）时才复制。
- 关键点：子返回 0、父返回子 pid；靠返回值判断父子，**不能判断调度先后**。
- 易错点：`fork` 后父子混用 `printf`，因 stdio 缓冲区被复制导致**重复输出**；不 `wait` 回收会留僵尸。

**Q2. 子进程不回收会怎样？怎么精确回收任意子进程？**
- 定位：不回收 → 僵尸进程（PCB 仍在，占进程表项）。
- 关键点：`waitpid(-1, &st, WNOHANG)` 非阻塞轮询回收任意子进程；没结束返回 0、不阻塞。
- 易错点：只调用一次会**漏回收**，要循环到返回 0 或 -1(ECHILD)。

**Q3. `exec` 做了什么？**
- 定位：替换当前进程映像，**PID 不变**（不新建进程），常与 `fork` 配合。
- 关键点：`execlp` 等变参函数最后一个参数必须 `NULL` 哨兵。
- 易错点：`exec` 成功后**后续代码永不执行**，只有失败才返回 -1。

**Q4. `SIGCHLD` 怎么异步回收僵尸？信号里能 `printf` 吗？**
- 定位：子进程退出时内核给父进程发 `SIGCHLD`。
- 关键点：handler 里 `waitpid` 异步回收；或 `signal(SIGCHLD, SIG_IGN)` 让内核自动回收（无需 wait）。
- 易错点：信号处理函数**不能调 `printf`**（非 async-signal-safe），要写日志用 `write`。

**Q5. `signal` vs `sigaction`？哪些信号不可捕获？**
- 定位：`signal` 在不同 UNIX 版本行为不一致（可能重置 handler），**不可靠**；`sigaction` 可靠。
- 关键点：`sigaction` 可设 `sa_mask`（处理时屏蔽其他信号）、`SA_RESTART`（自动重启被中断的系统调用）。
- 易错点：`SIGKILL`/`SIGSTOP` **不可捕获、不可忽略、不可屏蔽**；工程一律用 `sigaction`。

**Q6. `pause`/可重入/异步信号安全了解吗？**
- 定位：信号在任意指令间打断进程，handler 必须用可重入函数 + `volatile sig_atomic_t` 标志。
- 追问点：为什么在 handler 里改全局标志、在主循环里做实际处理（"信号只置位、业务在主流程"）？

## 二、IPC（6 题）

**Q7. 匿名 `pipe` 的特点和坑？**
- 定位：**亲缘进程**、半双工，`fd[0]` 读、`fd[1]` 写。
- 关键点：自带内核缓冲区，写满阻塞、读空阻塞。
- 易错点：不关闭用不到的 fd，读端**收不到 EOF**（写端引用计数没归零）。

**Q8. FIFO 和 pipe 的区别？**
- 定位：FIFO 是文件系统可见的节点，**无亲缘关系也能通信**。
- 关键点：`open` 会阻塞，直到读写两端都打开才返回。
- 易错点：`unlink` 删除节点后，**已打开的 fd 仍可正常通信**（inode 引用还在）。

**Q9. `mmap` 为什么是最快 IPC？**
- 定位：映射同一块物理页，**用户态直接读写、零拷贝**（最少的拷贝次数）。
- 关键点：`MAP_SHARED` 才真正共享，`MAP_PRIVATE` 是写时复制（改动不回写文件）。
- 易错点：`offset` 必须**页对齐**（通常 4096）；访问超出文件长度的映射区域会触发 **`SIGBUS`**。

**Q10. System V 共享内存 `shm` 的生命周期？**
- 定位：`shmget` 创建/获取、`shmat` 挂载到进程地址空间、`shmdt` 脱离。
- 关键点：**本身不提供同步**，必须配 mutex / 信号量（常放共享内存里）。
- 易错点：进程退出**不会自动删除** shm 段，要 `shmctl(IPC_RMID)` 或 `ipcrm` 手动清理。

**Q11. System V 消息队列 `msg` 的特点？**
- 定位：`msgget` 创建、`msgsnd`/`msgrcv` 收发，**带消息类型**。
- 关键点：`msgrcv` 可按 `msgtyp` **选择性接收**（不同类型优先级/过滤）。
- 易错点：队列有容量上限（`/proc/sys/kernel/msgmnb`），满了 `msgsnd` 阻塞（除非 `IPC_NOWAIT`）。

**Q12. IPC 怎么选型？**
- 口诀：**亲缘简单 → pipe；无亲缘流式 → FIFO；大数据低延迟 → mmap；带类型消息 → msg；计数同步 → sem**。
- 补充：跨网络 → socket；System V sem 的独特价值是**信号量集 + `semop` 原子操作多个 + `SEM_UNDO` 崩溃回滚**。

## 三、线程与同步（7 题）

**Q13. 线程和进程的区别？线程私有/共享什么？**
- 定位：线程共享进程地址空间（代码/数据/堆/fd），**通信靠全局变量、不用 IPC**；更轻量。
- 关键点：线程**私有**栈、寄存器、线程局部存储（TLS）。
- 易错点：多线程读写全局不加锁 → **数据竞争**（race）。

**Q14. mutex 怎么用？有哪些坑？**
- 定位：`pthread_mutex_t` 保护临界区，同一时刻仅一个线程持有。
- 关键点：使用前必须初始化（`PTHREAD_MUTEX_INITIALIZER` 或 `pthread_mutex_init`）。
- 易错点：**异常分支忘记 unlock**（用 RAII/ goto 统一出口）、重复解锁未持有的锁是 UB。

**Q15. `trylock` 的语义和坑？**
- 定位：非阻塞加锁，拿不到返回 `EBUSY` 而不挂起。
- 关键点：只有**拿到锁的线程才能 unlock**。
- 易错点：`trylock` 失败后若空转重试会**忙等烧 CPU**，应回退做别的事或加短暂让出。

**Q16. rwlock 读写锁的坑？**
- 定位：多读少写场景，**读共享、写独占**。
- 易错点①：**读锁不能直接升级写锁**（会自死锁，要先解锁再加写锁）。
- 易错点②：读者持续到来会让**写线程饥饿**（默认读者优先）。

**Q17. 条件变量 cond 为什么必须配 mutex、用 while？**
- 定位：等"某事件发生"，`pthread_cond_wait` 会**原子地释放 mutex 并挂起**。
- 三铁律：① 配 mutex ② 改完共享状态必 `signal` ③ 判断条件用 **`while` 非 `if`**（防虚假唤醒 / 被别的线程抢先）。
- 易错点：没加锁就调 `wait` 是 UB（可能直接崩溃）。

**Q18. semaphore 信号量怎么选型？`sem_init` 参数？**
- 定位：自带计数器，适合生产者消费者、限流。
- 关键点：`sem_init(&sem, pshared, value)`——`pshared==0` 表示**同一进程的线程间共享**（不是"线程内"）；非 0 用于进程间（须放共享内存）。另有有名 `sem_open` 供无亲缘进程使用。
- 易错点：**初值设错**导致逻辑全乱（互斥设 1、P-C 空位设缓冲区大小）；`post`/`wait` 要配对。

**Q19. 死锁的四个必要条件 + 解法？**
- 四要件（Coffman）：**互斥、占有且等待、不可剥夺、循环等待**（四个同时满足才死锁）。
- 解法优先级：**资源定序（破坏循环等待） > trylock + 回退（防活锁） > 一次性申请全部资源**。
- 追问点：为什么按统一顺序加锁能破坏循环等待？活锁和死锁的区别？

## 四、网络与并发模型（6 题）

**Q20. TCP 服务器完整流程？**
- 定位：`socket → setsockopt(SO_REUSEADDR) → bind → listen → accept → recv/send → close`。
- 关键点：网络字节序是**大端**，端口用 `htons`、IP 用 `htonl`/`inet_pton`。
- 易错点：不开 `SO_REUSEADDR`，重启时 `TIME_WAIT` 占用端口导致 `bind` 失败。

**Q21. UDP 和 TCP 的核心区别？**
- 定位：UDP 无连接、面向数据报；TCP 面向连接、可靠字节流。
- 关键点：**TCP `recv==0` 是对端关闭**（收到 FIN）；**UDP 收 0 只是空数据报**。UDP 无粘包，一次 recv 一个完整报文。
- 易错点：UDP 数据报**大于接收缓冲区会被截断、多余字节丢弃**；UDP 不感知对端生命周期（关服务端后客户端 `recvfrom` 永久阻塞）。

**Q22. 粘包/分包是什么？怎么解决？**
- 定位：TCP 是字节流、**不保留应用层消息边界**，多次 write 与 recv 次数无对应关系。
- 三解法：① **定长**（简单但浪费空间）② **长度字段**（先读够完整 header，解析出长度再循环读满 body——最常用）③ **分隔符**（如 `\n`，但数据里不能有该分隔符、不适合二进制）。
- 易错点：别假设"一次 recv 就是一个完整包"，必须循环读够。

**Q23. select / poll / epoll 三维度对比？**
- select：`fd_set` 位图，**上限 1024**，每次全量拷贝进内核 + O(n) 遍历。
- poll：用 `pollfd` 数组**突破 1024**，但仍全量拷贝 + O(n) 遍历。
- epoll：内核红黑树 + 就绪链表，注册一次、**只返回就绪 fd**，取就绪 O(就绪数)，适合海量 fd。

**Q24. LT vs ET？ET 为什么必须非阻塞 + 循环到 EAGAIN？**
- LT（水平触发）：就绪就持续通知，阻塞/非阻塞都行，不易丢事件。
- ET（边缘触发）：**只在状态变化时通知一次**；一次 recv 读不完后续不再通知 → 丢数据。
- 铁证：若 fd 是阻塞的，循环读到缓冲区空时 recv 会**挂起线程**（不是死锁）卡死 worker。所以必须**非阻塞 + 循环读到 -1 且 `errno==EAGAIN`**。

**Q25. 并发模型怎么演进？**
- 定位：多进程 → 每连接一线程 → 线程池 → I/O 多路复用 → **epoll + 线程池（工业主流）**。
- 关键点：线程池把"IO 等待"与"业务处理"解耦，固定线程数扛海量连接。
- 追问点：v3 线程池 worker 为何仍"占线程"？v4 怎么解？（见项目2讲稿 Q5）

## 五、高频八股（8 题）

**Q26. 三次握手？第三次能带数据吗？**
- 定位：`SYN → SYN+ACK → ACK`，同步双方初始序列号，确认双向收发能力。
- **第三次握手可以带数据**（发出时客户端已 ESTABLISHED，报文到达时服务端连接已建立）——协议允许且正常。
- 易错点：有风险的是**第一次 SYN 带数据**（SYN flood、数据重放），不是第三次；"第三次不推荐"的说法不准确。

**Q27. 四次挥手？为什么是 2MSL？**
- 定位：TCP 全双工，双向各发一次 FIN + ACK，共四次；**主动关闭方**进入 `TIME_WAIT`。
- 两个理由：① 最后 ACK 若丢失，被动方超时重发 FIN，主动方在 TIME_WAIT 期间还能**重发 ACK**；② 让本次连接产生的所有报文**在网络中消散**（MSL 是报文最大生存时间，2MSL 覆盖双向），避免新连接复用**同一四元组**时收到旧报文。
- 易错点：术语是**四元组**（源IP+源端口+目的IP+目的端口），不是"四进程组"。

**Q28. TCP 可靠传输靠什么？**
- 定位：校验和、**序号**、**确认应答 ACK**、**超时重传**、**滑动窗口（流量控制）**、**拥塞控制**。
- 关键点：丢包/乱序靠序号重排 + 重传；滑动窗口是端到端流量控制，拥塞窗口是网络侧拥塞控制。
- 追问点：快速重传和超时重传的区别？

**Q29. epoll 惊群？ONESHOT 的作用？**
- 定位：惊群 = 多个 waiter 被同一事件唤醒、只有一个真处理。
- 现状：**现代 Linux（2.6+）epoll_wait 惊群和 accept 惊群都已解决**；多个独立 epoll 实例监控同一 fd 时用 **`EPOLLEXCLUSIVE`**（4.5+，Nginx 在用）进一步优化。
- **ONESHOT 不是防惊群机制**（防惊群是内核的事），它保证**一个 fd 同一时刻只被一个 worker 线程操作**，防止多 worker 抢同一 fd 导致乱序/重复读。
- 易错点：ONESHOT 消费后必须 `EPOLL_CTL_MOD` **重新 ARM**（见项目2讲稿坑 #2）。

**Q30. 主线程 `return` / `pthread_exit` / 子线程 `return` 的区别？**
- 主线程 `return` **等价于 `exit()`**：终止整个进程，所有线程结束。
- 主线程 `pthread_exit()`：**只退出主线程**，其他线程继续；进程要等最后一个线程退出后才真正结束。
- 子线程 `return` **等价于 `pthread_exit()`**：只退出该子线程。

**Q31. 协程是什么？用户态/内核态切换？**
- 协程：**用户态调度**，内核不可见，不是内核线程；切换**不陷入内核**，开销远小于线程。
- 用户态→内核态由**系统调用、中断**触发，切换开销高；高并发场景尽量减少切换（如批量 IO、异步）。

## 六、最容易答砸的 8 题（红榜 · 修订版）

> 这 8 题是复盘时标红最多的，也是最容易被追问到卡壳的。必须脱稿讲清。

**红榜1｜TIME_WAIT 为什么是 2MSL（两个理由）**
① 保证最后的 ACK 可靠到达：若 ACK 丢了，被动方超时重发 FIN，主动方在 TIME_WAIT 期间还能重发 ACK，确保被动方正常关闭。② 让本次连接的所有报文在网络中消散，避免新连接复用**同一四元组**时被旧报文干扰。**（术语：四元组）**

**红榜2｜第三次握手能否带数据**
能带，协议允许且正常：第三次 ACK 发出时客户端已 ESTABLISHED，到达服务端时连接已建立。真正有风险的是**第一次 SYN 带数据**（SYN flood / 重放），不是第三次。

**红榜3｜粘包分包 + 三解法**
TCP 字节流不保留消息边界 → write 与 recv 次数无对应。解法：定长（浪费）、长度字段（先读够 header 再按长度循环读 body，最常用）、分隔符（不能含分隔符、不适合二进制）。

**红榜4｜ET 为什么必须非阻塞 + 循环到 EAGAIN**
ET 只在状态边沿通知一次，一次 recv 读不完后续不再通知 → 丢数据；若 fd 阻塞，读到缓冲区空时 recv 会**挂起线程**（不是死锁）卡死 worker。故必须非阻塞 + 循环读到 -1 且 `errno==EAGAIN`。

**红榜5｜死锁四要件 + 解法优先级**
互斥、占有且等待、不可剥夺、循环等待（同时满足才死锁）；解法：资源定序 > trylock 回退（防活锁）> 一次性申请全部资源。

**红榜6｜`pthread_exit` vs `main return`**
主线程 `return`=退出整个进程（所有线程终止）；主线程 `pthread_exit` 只退主线程、其他线程继续（进程等最后一个线程退出）；子线程 `return`=该子线程的 `pthread_exit`。

**红榜7｜System V sem vs POSIX sem**
优先 POSIX。POSIX 也能跨进程（`sem_init` 的 `pshared!=0` 放共享内存，或 `sem_open` 有名信号量）；System V 的独特价值是**信号量集 + `semop` 原子操作多个 + `SEM_UNDO` 崩溃回滚**。"多进程就必须 System V"是错的。

**红榜8｜epoll 惊群 + ONESHOT**
现代内核 epoll 惊群和 accept 惊群都解决了；多独立 epoll 实例监控同一 fd 用 `EPOLLEXCLUSIVE`。**ONESHOT 不是防惊群**，它保证**一个 fd 同一时刻只被一个线程操作**，防止多 worker 抢同一 fd 乱序；消费后必须 MOD 重新 ARM。
