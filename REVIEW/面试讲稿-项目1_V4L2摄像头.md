## 一、V4L2 基础与图像格式（6 题）

**Q1. V4L2 是什么？为什么不用 `read` 直接读摄像头？**
- 定位：Video4Linux2，Linux 视频设备的**统一用户态 API 框架**，`/dev/video*` 就是摄像头设备节点。
- 关键点：V4L2 **支持** read/write（三种 IO 之一），但 read 每帧要把数据从内核缓冲区**拷贝**到用户空间；高性能采集主流用 mmap 零拷贝，需要先协商分辨率/格式、维护缓冲区队列。
- 易错点：别说"V4L2 不能 read"——会被追问打脸。正确说法是"read 可用但多一次拷贝，所以主流选 mmap"。

**Q2. V4L2 三种 IO 方式？**
- 定位：read/write、mmap、userptr。
- 关键点：
  - **read/write**：每帧一次内核→用户拷贝，简单但开销大。
  - **mmap**：内核缓冲区映射到用户虚拟地址，**零拷贝**，硬件照常往内核缓冲写，用户从映射地址直接读——本项目用的就是这个。
  - **userptr**：用户态先分配内存，把地址交给内核直接写入，要求高（内存需页对齐、pin 住），少用。
- 易错点：mmap 是"映射同一块内核缓冲"，不是"拷贝到用户空间"——这俩别混。

**Q3. YUYV（YUY2）的内存布局？一帧多大？**
- 定位：YUV 4:2:2 的一种打包格式。
- 关键点：内存排列 `[Y0][U][Y1][V] [Y2][U'][Y3][V'] ...`——**4 字节出 2 个像素**，U/V 由水平相邻的两个像素共用。640×480 一帧 = `640*480*2 = 614400` 字节。
- 易错点：按 C 数组下标从 0 开始念是 `Y0 U0 Y1 V0`；写 `Y1 U0 Y2 V0` 是从 1 数，意思对但面试说标准写法。

**Q4. YUV 比 RGB 省多少？为什么用整数运算做转换？**
- 定位：YUV 把亮度(Y)和色度(UV)分离，4:2:2 每两个像素共用一组 UV。
- 关键点：YUYV 每像素平均 2 字节，RGB 每像素 3 字节，**省 1/3**。转换公式带浮点（1.402/0.344/0.714/1.772），嵌入式常无 FPU 或 FPU 慢，所以用**定点化**：系数×256、结果 >>8，精度损失 ≤1/256 肉眼看不出。
- 易错点：说"防止卡顿"太口语——背后的原理是**避免浮点运算开销**，这个才专业。

**Q5. FULL-RANGE 和 BT.601 limited-range 的区别？你的代码用哪个？**
- 定位：YUV→RGB 公式的两套取值范围。
- 关键点：我的 `yuyv_to_rgb` 用的是 **FULL-RANGE**（Y 0~255）公式，系数 359/88/183/454，配测试帧。真摄像头通常输出 **BT.601 limited-range**（Y 16~235、UV 128 居中），要先减 16/128，换系数 298/409/100/208/516。
- 易错点：**上真摄像头如果画面发灰、对比度不足，八成是这套公式没换**——这是我把坑写进代码注释的原因，面试能讲出来就是深度。

**Q6. MJPEG 和 YUYV 采集有什么区别？你的项目为什么选 YUYV？**
- 定位：摄像头可输出的两种常见格式。
- 关键点：YUYV 是**原始未压缩帧**，每帧大（614KB），但拿到就能做转换；MJPEG 是**压缩过的 JPEG 帧**，每帧小，但要解码才能处理。我的项目走 YUYV→RGB→libjpeg 编码存 jpg，格式统一、链路清晰。
- 易错点：别买"只输出 H.264 的摄像头"——M5 要用 RK 的 MPP 硬件编码，摄像头出原始帧才对。

## 二、V4L2 采集流程 8 步（7 题）

**Q7. 完整采集流程 8 步，默写出来。**
- 定位：V4L2 mmap 采集的固定骨架，面试白板必考。
- 关键点：
```
open → VIDIOC_QUERYCAP → VIDIOC_S_FMT → VIDIOC_REQBUFS
     → VIDIOC_QUERYBUF + mmap → VIDIOC_QBUF(全部入队) → VIDIOC_STREAMON
     → 循环[VIDIOC_DQBUF → 处理 → VIDIOC_QBUF] → VIDIOC_STREAMOFF → munmap + close
```
- 易错点：漏 `QBUF` 归还、漏 `S_FMT` 读回确认——这两个是最高频扣分点。

**Q8. `VIDIOC_QUERYCAP` 查什么？**
- 定位：查询设备能力，确认这是不是能流式采集的视频设备。
- 关键点：看三个标志——`V4L2_CAP_VIDEO_CAPTURE`（是不是采集设备）、`V4L2_CAP_STREAMING`（支不支持流式 IO）、`V4L2_CAP_READWRITE`（支不支持 read）。
- 易错点：只查一个标志就往下走，设备不支持时会一路错下去。

**Q9. `S_FMT` 之后为什么要读回来确认？（坑位 #3）**
- 定位：向内核请求宽高/像素格式。
- 关键点：驱动**可能改写你的请求**（你请求 1920×1080 它给 1280×720，或不支持 YUYV 给你 MJPEG），所以 `ioctl(S_FMT)` 后必须读 `fmt.fmt.pix` 的真实宽高/格式，后续缓冲大小和转换都按真实值算。
- 易错点：直接用请求的 WIDTH/HEIGHT 算缓冲 → 缓冲错位、花屏。我代码里 `real_w/real_h` 就是从读回值来的。

**Q10. `v4l2_requestbuffers` 有哪些字段？`m.offset` 在哪个结构体？**
- 定位：申请缓冲区 vs 描述单块缓冲，两个结构体字段别混。
- 关键点：
  - `v4l2_requestbuffers`：`count`（缓冲数）、`type`（如 `V4L2_BUF_TYPE_VIDEO_CAPTURE`）、`memory`（如 `V4L2_MEMORY_MMAP`）——**没有 offset**。
  - `v4l2_buffer`：`index`、`bytesused`、**`m.offset`**（mmap 时用）、`length`、`timestamp`。
- 易错点：我复盘时把 offset 记到了 requestbuffers 里——面试一起考这两个，一定分清。

**Q11. `mmap` 那一步怎么把内核缓冲映射到用户态？**
- 定位：把内核缓冲区的偏移映射成用户可访问的虚拟地址。
- 关键点：`mmap(NULL, buf.length, PROT_READ|PROT_WRITE, MAP_SHARED, fd, buf.m.offset)`——offset 来自 `QUERYBUF` 填的 `buf.m.offset`，长度用 `buf.length`，映射后的地址存进 `buffers[index]` 供 DQBUF 后按 index 取用。
- 易错点：`MAP_FAILED` 要检查（不是 NULL）；每块缓冲都要单独 mmap。

**Q12. `DQBUF` 后为什么要 `QBUF` 归还？（坑位 #4）**
- 定位：出队取一帧 → 处理 → 必须把缓冲还给内核。
- 关键点：4 块缓冲轮转，取走不归还，几轮后队列耗尽，`DQBUF` **永久阻塞**卡死线程。归还前还要检查短帧（`bytesused` 不足就归还后 continue，别拿残数据转换）。
- 易错点：我代码里短帧分支和正常分支**各归还一次**，两条路径都不能漏；归还的 `ioctl` 还要查返回值。

**Q13. `STREAMON/STREAMOFF` 做什么？为什么 cleanup 要用 `stream_on` 标志？**
- 定位：开启/关闭摄像头数据流。
- 关键点：`STREAMON` 后内核才开始往队列缓冲填数据；`STREAMOFF` 停止采集。
- 易错点：如果 `open` 成功但某步就 goto cleanup 了（流根本没开），无条件调 `STREAMOFF` 会失败——所以我加了 `int stream_on=0`，成功后置 1，cleanup 里只在为 1 时关流。

## 三、图像处理与落盘（4 题）

**Q14. `yuyv_to_rgb` 的核心逻辑？**
- 定位：纯算法函数，只吃"一块 YUYV 缓冲 + 宽高"，与帧源无关。
- 关键点：每轮读 4 字节 `y0=p[0], u=p[1]-128, y1=p[2], v=p[3]-128`（注意 Y1 是 p[2] 不是 p[1]），算 `r_off=(359*v)>>8` 等，输出 2 个像素共 6 字节，`p+=4; q+=6`。
- 易错点：抄 AI 代码时我把 `y1` 写成 `p[1]`（那是 U）——隔一个像素亮度错乱；这类笔误编译器抓不到，靠逐行审查。

**Q15. libjpeg 编码一帧的九步？**
- 定位：把 RGB 缓冲编码成 jpg 落盘的固定流水线。
- 关键点：① 声明 `jpeg_compress_struct cinfo` + `jpeg_error_mgr jerr` ② `cinfo.err=jpeg_std_error(&jerr)`（**必须第一步挂错误处理**）③ `jpeg_create_compress` ④ `jpeg_stdio_dest(cinfo,fp)` ⑤ 填 `image_width/height/input_components=3/in_color_space=JCS_RGB` ⑥ `jpeg_set_defaults` + `jpeg_set_quality` ⑦ `jpeg_start_compress` ⑧ 循环 `jpeg_write_scanlines(&row,1)` **一次喂一行** ⑨ `jpeg_finish_compress`→`jpeg_destroy_compress`→`fclose`。
- 易错点：字段名是平铺的 `cinfo.image_width`（不是 `cinfo.image.width`）；`input_components` 有 s；`jpeg_write_scanlines` 有 s；`fclose(fp)` 不是 `fclose(fd)`——这些我全打错过，白板注意。

**Q16. `jpeg_write_scanlines` 为什么一次喂一行？stride 怎么算？**
- 定位：libjpeg 按扫描行写入。
- 关键点：`JSAMPROW row = rgb + next_scanline * stride`，`stride = w*3`（每像素 3 字节），循环到 `next_scanline == image_height`。
- 易错点：把 stride 当成 w（漏乘 3）→ 图像错位。

**Q17. 你的处理链怎么做到"换帧源不动处理代码"？**
- 定位：采集/处理解耦是本项目的核心架构点。
- 关键点：`yuyv_to_rgb`/`write_jpeg` 只吃"一块 YUYV 数据 + 宽高"，不知道帧从哪来。软件模拟帧喂的是内存数组，真摄像头喂的是 `DQBUF` 出队的 mmap 地址——**函数一行不改**。
- 易错点：面试要讲出"接口边界"——`image_proc.c` 是处理层，`image_camera.c`/`multi_camera.c` 是帧源层，两层通过帧缓冲对接。

## 四、工程化设计（5 题）

**Q18. `FAKE_CAPTURE` 开关怎么实现的？为什么这样设计？**
- 定位：用条件编译切换真/假帧源，让没硬件时也能验证整条数据流。
- 关键点：`#ifndef FAKE_CAPTURE #define FAKE_CAPTURE 1 #endif` 提供默认值，命令行 `-DFAKE_CAPTURE=0` 可覆盖；帧源收敛成 `acquire_frame`/`release_frame` 两个接口，条件编译**只在接口内部**，循环体一个 `#if` 都没有。
- 易错点：源文件里不能硬写 `#define FAKE_CAPTURE 1`——会撞命令行覆盖。我第一版就写死了，改成 `#ifndef` 包裹才行。

**Q19. 为什么把条件编译放在接口内部，而不是循环里？**
- 定位：可测试性设计。
- 关键点：循环里写一堆 `#if` 会把逻辑切得稀碎、极易错；收敛成接口后，调用方（循环）永远只看到"取帧/处理/归还"三步，不知道帧从真假。这是**面向接口编程**。
- 易错点：我一开始想用 `#if` 切循环体，自己都绕晕了——收敛成两个函数是打破死局的关键。

**Q20. `image_proc.c/.h` 模块化怎么做的？**
- 定位：把处理链从主程序抽成独立模块。
- 关键点：头文件放声明 + include guard + 契约注释（缓冲谁分配、返回值含义）；实现文件去掉 `static` 让它跨文件可见，`clamp255` 保持 `static inline` 留在内部；两个主程序链接同一个 `.c`。
- 易错点：抽模块最容易"忘了删原函数导致重复定义"或"头文件忘了 include guard"——编译器会直接报。

**Q21. 什么是背压/为什么要有上限？**（可关联项目2 的 EPOLLOUT）
- 定位：防止慢消费者拖垮系统。
- 关键点：我的多线程版队列是 4 槽固定大小，队列满时生产者 `cond_wait(not_full)` 等待——这就是一种背压，内存有上限。项目2 的 `OUTBUF_MAX=8192` 同理。
- 易错点：别为了"不丢帧"无限缓冲内存——要有上限，超过就阻塞或丢弃，这是工程取舍。

**Q22. 你踩过最印象深刻的坑是什么？**
- 定位：面试官必问"遇到什么困难"，要讲真坑 + 真解法。
- 关键点：首选 **"AI 生成的代码也有 5 个 bug"**——我从别的 AI 搜来 softcam 跟着敲，review 出 5 处错误（少 `*`、`(path,"wb")` 少 fopen、`jpeg_std_error` 少调用、`y1=p[1]`、malloc 失败没 return），后来自己写 camera 又手滑 3 处。**结论：过手敲 + 逐行审查 + 编译验证，比"AI 说对"可靠，编译器是最便宜的审查员。**
- 易错点：别讲"很容易就搞定了"——讲真踩的坑、怎么定位、怎么修，才显得有实战经验。

## 五、多线程采集编码（5 题）

**Q23. 你的多线程架构？**
- 定位：生产者消费者，把"采集"和"存图"解耦。
- 关键点：采集线程（生产者）只管 `acquire_frame` 塞帧 → 4 槽环形队列（mutex + `not_empty`/`not_full` 两个 cond）→ 编码线程（消费者）取帧做 YUYV→RGB→存 jpg。**存图不再阻塞采集**——这是流水线思想。
- 易错点：单线程版存 jpg 时采集被阻塞（jpeg 编码慢）；多线程版两个线程各干各的。

**Q24. 环形队列为什么用两个条件变量？**
- 定位：`not_empty`（有帧了唤醒消费者）、`not_full`（有空位了唤醒生产者）。
- 关键点：生产者队列满时 `wait(not_full)`，消费者取走帧后 `signal(not_full)`；消费者队列空时 `wait(not_empty)`，生产者塞帧后 `signal(not_empty)`。两个 cond 各管一侧，避免忙等。
- 易错点：`cond_wait` 必须用 **`while` 不是 `if`**（虚假唤醒）；解锁后再做 jpeg 编码（持锁 = 串行，失去并行意义）。

**Q25. 生产者消费者 + 复用缓冲的经典坑？（坑位 #7）**
- 定位：假帧源共用一块 `g_fake_yuyv`，每帧覆盖。
- 关键点：采集线程**必须 `memcpy` 把帧拷进队列自己的槽位**，不能直接把指针塞进队列——否则消费者还没处理，缓冲就被下一帧覆盖，存出来的图全一样。真模式 DQBUF 循环同理。
- 易错点：这是"生产者消费者 + 复用缓冲"最经典的坑，我设计 8 色彩条 + 帧号白块就是为了肉眼验证 5 张图不同。

**Q26. 线程怎么优雅退出？（M3 老朋友）**
- 定位：采集完置 stop → 广播唤醒 → join 回收。
- 关键点：生产者采集完置 `g_q.stop=1` + `cond_broadcast` 两个 cond；消费者 `while(count==0 && !stop) wait`，退出条件是 `count==0 && stop`（**先把队列剩帧处理完再退出**）；main `pthread_join` 两个线程。
- 易错点：消费者退出判断后必须 `break`，否则 `count--` 变负、死循环不退出、`join` 永远卡住——我踩过。

**Q27. 怎么证明你的多线程真的并行了？**
- 定位：用 `time` 的输出。
- 关键点：`real 0.567s / user 0.711s`——**user > real** 说明两个线程在不同 CPU 核上同时跑，用户态 CPU 时间累加超过了墙钟时间。单线程的话 user 一定 ≤ real。
- 易错点：这是个很有说服力的细节，面试主动讲出来，比空说"我用了多线程"强。

**Q28. valgrind 验证了什么？**
- 定位：内存泄漏检测。
- 关键点：`valgrind --leak-check=full ./multi` 输出 `in use at exit: 0 bytes`、`84 allocs / 84 frees`、`All heap blocks were freed -- no leaks are possible`、`0 errors`——证明预分配的 4 槽 + rgb + g_fake_yuyv 全配对释放。
- 易错点：valgrind 慢，测的时候把帧数改回 5，别跑 100 帧。

## 六、硬件选型与项目叙事（4 题）

**Q29. 为什么选 RK3568？**
- 定位：芯片选型理由。
- 关键点：与 RK3566 在项目用到的能力**完全相同**（四核 A55、1TOPS NPU、4K@60 解码、1080p@60 H.264/H.265 硬编码、8M ISP），多出的双网口/PCIe3.0/三屏/SATA 项目用不上；但作为**安防视觉主流平台**，资料生态更好、岗位对口度更高。别上 RK3588（贵 2-3 倍，算力用不上）。
- 易错点：别背参数清单——讲"项目用不到那些差异，但资料生态值钱"这个取舍逻辑。

**Q30. 你这块板子的配置？为什么够用？**
- 定位：正点原子 AtomPi-CA1，闲鱼 ¥680（原价 ¥789），2GB + 32GB eMMC。
- 关键点：**2+32G 对这个项目绰绰有余**——V4L2 一帧 640×480 YUYV 才 614KB，libjpeg 编码几百 KB，2GB 内存富余；32GB 装 Debian + 工具链 + 存图足够。买的是正点原子的**资料确定性**（教程/SDK/MPP 例程全）。
- 易错点：别为"不是 4G 内存"心虚——真正的红线是 2+8G（8GB eMMC 装系统会见底），2+32G 不触及。

**Q31. UVC 摄像头为什么即插即用？**
- 定位：USB Video Class 标准驱动。
- 关键点：UVC 是 Linux **标准驱动**，插上 USB 摄像头 `/dev/video0` 就出现，跟厂商"适没适配"无关。所以选板子只要确认有 USB 口即可，不必纠结"厂商有没有摄像头例程"。
- 易错点：别买 MIPI 排线摄像头（要改设备树，坑多）；确认是 USB UVC、支持 MJPEG/YUY2。

**Q32. 一句话讲清项目1（30 秒口述）。**
- 定位：面试开场的项目概述。
- 关键点：
> "我做了一个基于 RK3568 的 V4L2 摄像头采集项目。用 **mmap 零拷贝**方式走完 8 步 ioctl 采集流程，把 YUYV 帧做**整数定点**转 RGB 后用 libjpeg 存成 jpg。为了让没硬件时也能验证，我把帧源抽象成接口、用**条件编译**切换真假帧源，在本机跑通了整条数据流。进一步用**生产者消费者 + 环形队列**把采集和存图解耦，100 帧稳定性验证不丢帧、valgrind 零泄漏。板子上只需切换宏、换真实设备节点，处理链一行不改。"
- 易错点：背熟这条主线——**采集→转换→落盘→多线程→可测试性→可移植**，30 秒讲完，细节留给追问。

## 七、最容易答砸的 8 题（红榜 · 必须脱稿）

| # | 题 | 最容易栽的点 |
|---|----|------------|
| 1 | Q7 8 步流程 | 漏 `QBUF` 归还 / 漏 `S_FMT` 读回 |
| 2 | Q10 两个 buffer 结构体 | 把 `m.offset` 记到 `requestbuffers` 里（它没有 offset） |
| 3 | Q4/Q5 整数定点 + range | 说"防卡顿"不讲 FPU；不知道真摄像头要换 limited-range 系数 |
| 4 | Q15 libjpeg 九步 | 字段名拼错（`image.width`/`input_commponents`/`fclose(fd)`） |
| 5 | Q19 条件编译边界 | 说不清为什么放接口内部而不是循环里 |
| 6 | Q25 复用缓冲坑 | 讲不出"必须 memcpy 拷进槽位"的原因 |
| 7 | Q26 优雅退出 | 消费者漏 `break` → count 变负死循环（我踩过） |
| 8 | Q27 真并行证据 | 不知道 `user > real` 意味着多核并行 |

> 口诀：**采集八步要念全，S_FMT 读回、QBUF 还；转换定点避浮点，真机还得换 range；帧源接口切真假，拷贝进槽别塞指针；退出广播加 join，user 大于 real 才叫并行。**
