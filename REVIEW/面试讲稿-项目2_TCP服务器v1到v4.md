# 面试讲稿 · 项目2：Linux TCP 服务器（v1→v4 架构演进）

> 用途：把 v1→v4 的"为什么这么演进 + 每个版本踩过的坑 + 面试怎么答"串成一份可背诵的讲稿。
> 配合代码仓库 `linux-tcp-server`（v1/v2/v3/v4 全部可编译运行）使用。
> 用法：先照"开场白"练，再逐版本过"口述模板"，最后用文末"模拟面试自测题"闭卷自测。

---

## 0. 开场白（30 秒版，背下来）

> 我做了一个从零实现的 Linux 网络服务器项目，核心**不是一次写个完美服务器，而是同一需求下逐步演进架构**——v1 阻塞单连接、v2 每连接一线程、v3 线程池、v4 epoll+线程池。每一版都为了解决前一版的瓶颈，用来体会不同并发模型的取舍。这正好是后端 / Linux 开发面试最爱追问的脉络：**从"能跑"到"能扛量"是怎么走过来的**。

---

## 1. 整体演进表（一眼看懂）

| 版本 | 并发模型 | 并发能力 | 解决的核心问题 | 遗留瓶颈 |
|------|----------|----------|----------------|----------|
| v1 | 阻塞单连接（回声） | 0（一次只服务 1 个客户端） | 跑通 socket 全套流程 | 串行，第二个客户端得等第一个断开 |
| v2 | 多线程（每连接一线程 · 聊天室） | 高（每连接独立线程） | 连接真正并发 | 连接数=线程数，C10K 时线程爆炸、上下文切换开销大 |
| v3 | 线程池（预创建 worker + 任务队列） | 高（可控线程数） | 避免"每连接建线程"的开销与失控 | worker 拿到 fd 后**阻塞 recv** 仍占住线程，4 个 worker 同时只能服务 4 个"正在 recv"的连接 |
| v4 | epoll + 线程池（IO 多路复用） | 很高（单线程管上万 fd） | 把 **IO 等待与业务处理解耦** | 已是标准高并发骨架（再往后才是 reactor/proactor、用户态协程等） |

**一句话总结演进**：v1 一次只能服务一个客户端 → v2 用多线程让连接并发 → v3 用线程池避免"每连接建线程"的开销与失控 → v4 用 epoll 把 IO 等待交给内核，线程池只做处理，**少量固定线程扛海量连接**。

## 2. 逐版本讲解 + 面试追问

### v1 · 阻塞单连接回声服务器

**口述模板**：
> "v1 是最朴素的版本，目的是跑通 TCP 服务器的完整生命周期：`socket → bind → listen → accept → recv/send → close`。它是阻塞模型——`accept` 阻塞等连接，`recv` 阻塞等数据，一次只能服务一个客户端，第二个客户端连上来也得排队。"

**面试追问 & 标准答**：
- **为什么 `send` 要放在循环里？**
  > TCP 是字节流，内核发送缓冲区可能一次写不下。比如要发 4096 字节但缓冲区只剩 1000，`send` 只发 1000 返回，剩下必须循环补发（处理"短写 / partial write）。不循环就会丢数据。
- **`SO_REUSEADDR` 干嘛用的？**
  > 服务器重启时，上一次的 socket 处于 `TIME_WAIT` 状态会占用端口，`bind` 报 `Address already in use`。设了它就允许复用，重启不卡。
- **`recv` 被信号打断返回 -1 怎么办？**
  > `errno==EINTR` 时应重试，而不是当错误处理关连接。

---

### v2 · 多线程聊天室（每连接一线程）

**口述模板**：
> "v2 让连接真正并发：每来一个客户端，`pthread_create` 起一个线程专门服务它，主线程继续 `accept` 下一个。为了让线程结束自动回收、不堆积僵尸线程，我用 `pthread_detach` 让线程自回收。聊天室需要群发，所以我维护了一个全局客户端数组 `g_clients[]`，用 `pthread_mutex_t` 保护，任意客户端发消息都 `broadcast` 转发给其他人。"

**面试追问 & 标准答**：
- **为什么 detach 而不是 join？**
  > 每连接一线程是"来一个建一个"，主线程没法预知哪个线程先结束，join 会阻塞主线程。detach 让线程跑完自己释放资源，主线程不被拖住。
- **线程间共享的客户端表怎么保证安全？**
  > 所有对 `g_clients[]` 的读写都包在互斥锁里，避免两个线程同时增删客户端导致竞态。
- **线程间怎么传客户端 fd？**
  > 用 `malloc` 拷一份值传进去，线程内 `free`。**不能传栈上地址**——主线程的栈变量在线程读到之前可能已经被覆盖/失效，造成数据竞争。
- **为什么忽略 `SIGPIPE`？**
  > 客户端已经断开，服务端还往这个 socket `send`，内核会发 `SIGPIPE` 默认杀进程。忽略它，让 `send` 返回 `EPIPE` 由代码优雅处理。

---

### v3 · 线程池回声服务器

**口述模板**：
> "v2 的致命问题是连接数=线程数，C10K 时线程爆炸、上下文切换开销压垮性能。v3 改成**线程池**：启动时预创建固定数量（我设了 4 个）常驻 worker 线程，主线程 `accept` 拿到连接后，只把 fd `malloc` 拷一份投进**任务队列**，worker 自己从队列取任务处理。这样线程数量与连接数解耦，不会失控。"

**面试追问 & 标准答**：
- **为什么用线程池而不是每连接一线程？**
  > 线程的创建/销毁有开销，海量短连接下频繁建线程比处理业务还贵；且线程数无上限会耗尽系统资源。线程池用固定数量的常驻线程削峰。
- **条件变量 `cond_wait` 为什么必须用 `while` 而不是 `if`？**
  > 防止"虚假唤醒"（spurious wakeup）——被唤醒后条件可能并不满足（比如被别的线程抢先取走了任务）。`while` 重新检查条件才安全。这是条件变量的标准写法。
- **锁应该包多大范围？**
  > **只包"取/放任务"那几行**（操作队列），绝不把 `recv/send` 包在锁里。否则 worker 持锁做 IO，并发直接退化成串行，线程池失去意义。
- **怎么优雅退出？**
  > 设 `stop` 标志，`pthread_cond_broadcast` 唤醒所有阻塞的 worker，每个 worker 取到"空队列+stop"后退出，主线程 `pthread_join` 等它们收尾，最后 `destroy` 锁和条件变量。

### v4 · epoll + 线程池（项目终极形态）

**口述模板**：
> "v3 还有个短板：worker 拿到 fd 后是用**阻塞 `recv`** 卡在 IO 上的，4 个 worker 同时只能服务 4 个'正在 recv'的连接，第 5 个连上来也得等。v4 把 IO 等待从线程里抽出来，交给 **epoll**：主线程跑一个 epoll 事件循环，一处盯所有 fd（监听 fd + 全部客户端 fd），**只在某个 fd 真正'可读'时才把 fd 丢给线程池**；worker 拿到 fd 后专心'读+回声'。这样** IO 等待与业务处理解耦**，少量线程就能扛海量连接。"

**v4 核心机制（逐点讲）**：
1. `listenfd` 用 `EPOLLIN`（LT 水平触发）注册——单次 `accept` 安全，没 accept 完下一轮还会通知。
2. `clientfd` 用 `EPOLLIN | EPOLLONESHOT` 注册——触发一次后自动关闭通知，直到 worker 处理完用 `EPOLL_CTL_MOD` **重新 ARM**。
3. 主线程只在 fd 可读时 `enqueue(fd)`，自己**不读数据**。
4. worker 取到 fd → **非阻塞 `recv` 循环读到 `EAGAIN`**（读干净）→ `send` 回声 → `EPOLL_CTL_MOD` 重新 ARM，等下次可读。

**面试追问 & 标准答**：
- **v3→v4 的本质区别是什么？**
  > v3 是"每连接阻塞 recv 占线程"，线程数受限于"同时在进行 IO 的连接数"；v4 是"epoll 统一等待 IO + 线程池只做处理"，线程数只取决于 CPU 业务量，与连接数无关。
- **为什么 epoll + 线程池能扛海量连接？**
  > epoll 一个线程就能监视上万 fd（内核用红黑树+就绪链表，取就绪事件是 O(1)），而线程池规模固定（比如 4~8 个，对齐 CPU 核数），不会因连接多而爆线程。
- **`EPOLLONESHOT` 为什么需要？**
  > 没有它，一个 fd 的可读事件可能被多次上报、被多个 worker 同时拿到，导致两个线程抢同一 fd、数据乱序/重复读。ONESHOT 保证**同一时刻只有一个 worker 在动这个 fd**，处理完再手动重新打开通知。这是 epoll+线程池避免竞态的标准答案。
- **LT vs ET 在本项目怎么选？**
  > 我 v4 用的是 **LT + ONESHOT**，简单稳妥——LT 下没读干净下次还会通知，不容易丢事件。若追求极致性能可换 ET，但 ET 必须配**非阻塞 fd + 循环读到 EAGAIN**，否则会丢数据、坑更多。我之前单独写过 LT/ET 两个 demo 对比过（见 `practice/M3D19_epoll/`）。

## 3. 跨版本高频面试题（综合）

- **select / poll / epoll 三者对比？**
  > select 用 `fd_set` 位图，写死 1024 上限，每次调用都要把全量 fd 拷贝进内核、返回后还得 O(n) 遍历；poll 用 `pollfd` 结构突破 1024，但仍全量拷贝+O(n) 遍历；epoll 是内核维护的红黑树+就绪链表，注册一次、之后 `epoll_wait` 只返回就绪的，取就绪 O(1)，支持海量 fd，还能选 LT/ET 触发模式。
- **阻塞 IO vs 非阻塞 IO？**
  > 阻塞：调用后线程挂起直到数据就绪，编程简单但占线程；非阻塞：立即返回，配合 epoll 才能让一个线程管多个 fd，但必须循环读到 `EAGAIN` 才算读干净。
- **惊群（thundering herd）了解吗？**
  > 多个进程/线程同时 `epoll_wait` 同一个 fd，事件到来时全部被唤醒、只有一个能处理，其余白醒。可提：本项目的 worker 用 ONESHOT + 任务队列已经规避了"多 worker 抢同一 fd"；epoll 本身在现代内核已做惊群优化。
- **为什么网络服务器要忽略 `SIGPIPE`、区分 `EINTR`？**
  > 见 v2/v4 答法，属于服务器健壮性的基本功。

## 4. 踩坑实录（我写这个项目时真实踩过，面试讲出来很加分）

| # | 坑 | 现象 | 根因 | 修法 |
|---|----|------|------|------|
| 1 | v3/v4 worker 用 `break` 退出线程 | 服务完一个连接 worker 线程就死，最多只能服务 4 个客户端 | `break` 跳出了 `while(1)` 线程主体 | worker 必须**常驻循环**，所有"这个 fd 处理完"的分支用 `continue` 回顶部等下一个任务 |
| 2 | v4 `EPOLLONESHOT` 消费后不重新 ARM | **同一客户端第二条消息起全部不回声**（连接"假死"） | ONESHOT 触发一次后通知被关闭，没 `EPOLL_CTL_MOD` 重新打开就再也不通知 | 处理完 fd 必须 `EPOLL_CTL_MOD` 重新 ARM（EAGAIN/EINTR 要"穿透"到这段，不能 `continue` 跳过） |
| 3 | send 失败仅 `break` 未 `DEL+close` | fd 泄漏 + epoll 忙等 | 出错路径只跳出了内层循环，外层又对失效 fd 操作 | send 失败：`EPOLL_CTL_DEL` + `close`，并标记 `fd=-1` 跳过后续判断 |
| 4 | recv 返回 -1 未区分 `EINTR` | 被信号轻微打断就误关连接 | 把 `EINTR` 当真错处理 | `errno==EINTR` 应重试（continue 而非关连接） |
| 5 | 持锁做 IO | 并发退化成串行，线程池失效 | 把 `recv/send` 包进 `mutex` | 锁只包"取/放任务" |
| 6 | 队列满时 fd 成孤儿 | fd 已 `EPOLL_CTL_ADD` 但任务没入队，再也不被处理 | enqueue 失败没兜底清理 | enqueue 失败（malloc 失败 / 队列满）时 `EPOLL_CTL_DEL` + `close` 兜底 |
| 7 | ET 模式事件循环用 `break` 退出 for | 同一次 `epoll_wait` 返回的多个就绪 fd 被丢弃，个别客户端数据卡死 | `break` 退出了"处理就绪事件"的 for 循环，不是只读循环 | ET 下处理完一个 fd 用 `continue` 处理下一个，绝不 `break` |

> 记忆口诀：**ONESHOT 必重挂，worker 别退场；send 出错要 DEL+close，EINTR 重试别慌；锁只包队列，IO 往外放。**

## 5.1 自测参考答案（闭卷后对照）

> 以下为第 5 节 10 道题的口述参考答案。先闭卷自测、卡住再回看。

1. **v1→v4 各解决什么瓶颈**
   - v1：阻塞单连接，一次只服务 1 个客户端，第二个得排队。
   - v2：每连接一线程，让连接真正并发，但连接数=线程数，C10K 时线程爆炸、切换开销大。
   - v3：线程池（固定常驻 worker + 任务队列），避免"每连接建线程"的开销与失控；但 worker 阻塞 `recv` 仍占线程，同时只能服务 N 个"正在 recv"的连接。
   - v4：epoll 把 IO 等待从线程里抽出来交给内核，线程池只做业务处理，**少量固定线程扛海量连接**。

2. **v2 为什么 `pthread_detach` 而非 `join`**
   - 每连接一线程是"来一个建一个"，主线程没法预知哪个先结束，`join` 会阻塞主线程。detach 让线程跑完**自己释放资源（避免僵尸线程）**，主线程不被拖住。

3. **线程间传 fd 为什么 `malloc` 拷值、不能传栈地址**
   - `pthread_create` 后主线程继续循环，那个栈变量（fd）的栈帧随时可能被复用/回收，子线程读到时已是悬空指针或已被覆盖（数据竞争）。必须堆上 `malloc` 一份值传进去，线程内 `free`。

4. **`cond_wait` 为什么用 `while` 而非 `if`**
   - 防止**虚假唤醒（spurious wakeup）**：被唤醒后条件可能并不满足（被别的线程抢先取走任务）。`while` 重新检查条件才安全，这是条件变量标准写法。

5. **v3 worker 为什么"占住线程"，v4 怎么解**
   - v3 worker 拿到 fd 后**阻塞 `recv` 卡在 IO 上**，线程被 IO 等待占住，同时能服务的连接数 = worker 数。
   - v4 用 **epoll（主线程）统一监视上万 fd**，只在 fd 真正可读时才把 fd 丢给线程池；worker 只做 recv+send 业务、**不等待 IO**，所以线程数只取决于 CPU 业务量，与连接数解耦。

6. **`EPOLLONESHOT` 解决什么竞态？不重挂会怎样**
   - 没有它，一个 fd 的可读事件可能被多次上报、被**多个 worker 同时拿到 → 两线程抢同一 fd、乱序/重复读**。ONESHOT 保证**同一时刻只有一个 worker 在动这个 fd**，处理完必须 `EPOLL_CTL_MOD` 重新 ARM。
   - 不重挂（坑 #2）：该 fd 后续数据再也不被通知 → **同一客户端第二条消息起全部不回声（连接假死）**。

7. **LT vs ET？ET 为什么必须非阻塞 + 循环读 EAGAIN**
   - LT（水平触发）：只要缓冲区还有数据没读完，`epoll_wait` 每次都返回该 fd → 一次没读干净下次还通知，**不易丢数据、好写**。
   - ET（边缘触发）：只在"不可读→可读"的边沿通知一次，之后即使有残留数据也不再通知，除非有新数据到达。所以 ET **必须** ① fd 设非阻塞（避免 recv 阻塞卡死）② **循环 recv 读到 `EAGAIN`** 才算读干净，否则残留数据永不被唤醒 → 丢数据/卡死。
   - 取舍：ET 事件次数少、高并发系统调用开销低、性能更极致，但编程严、坑多；LT 稳。本项目 v4 选 **LT + ONESHOT** 求稳。

8. **select/poll/epoll 三维度对比**
   - select：fd 上限 **1024（FD_SETSIZE 写死）**；每次调用**全量 fd 拷贝进内核**（O(n)）；取就绪 **O(n) 遍历**所有 fd 判断是否就绪。
   - poll：用 `pollfd` 结构**突破 1024**；仍**全量拷贝（O(n)）**；取就绪 **O(n) 遍历**。
   - epoll：**无硬上限（海量）**；**无全量拷贝**（注册一次，fd 常驻内核红黑树+就绪链表，`epoll_wait` 只把**就绪事件**拷出）；取就绪 **O(就绪事件数)**，只返回就绪的、不用遍历全部；还能选 LT/ET。

9. **为什么忽略 `SIGPIPE`、区分 `EINTR`**
   - 客户端已断开，服务端还往该 socket `send` → 内核发 `SIGPIPE`，**默认动作是杀进程** → 忽略它，让 `send` 返回 `EPIPE` 由代码优雅处理。
   - `EINTR` 是系统调用被信号**打断**返回 -1，不是真错，应**重试**而非关连接。

10. **v4 能扛多少并发？瓶颈在哪**
    - 连接数：上万级没问题（epoll 一个线程监视海量 fd，连接等待不占线程）。
    - 但"能同时处理的业务请求数"≈ **线程池大小**（应**对齐 CPU 核数**，如 8），瓶颈不在连接数而在"同时做业务的请求数"。
    - 真实瓶颈点：① 线程池大小/CPU 核数（单业务耗时会占 worker、队列积压）；② **慢客户端 `send` 占 worker**（应改 `EPOLLOUT` 等可写再发）；③ 目前 LT，海量活跃连接事件次数偏多，极致吞吐可评估 ET；④ 无连接超时/心跳/应用层协议（仅行式回声）。
    - 收尾：v4 已扛"海量连接+适度并发"，继续优化方向即上述几点。

---

## 6. 收尾话术（面试官追问"你这个项目有什么不足 / 还能怎么优化"时）

> "目前 v4 是 LT + 阻塞式业务处理的经典 reactor 模型，已经能扛高并发连接。如果要继续优化，我会考虑几个方向：一是把 worker 里的业务处理也异步化、或按 CPU 核数对齐线程数避免上下文切换；二是如果要更极致吞吐，可以评估 ET 模式减少 epoll 事件次数；三是真正的生产服务器还会加：连接超时回收、心跳保活、协议层分包（目前是行式回声，没有应用层协议）、以及用 `EPOLLOUT` 改造解决 `send` 阻塞。这些是我下一步的演进思路。"
